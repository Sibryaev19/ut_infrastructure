Какие данные скачиваются из Jira и на чём считаются метрики
============================================================

Коротко о конвейере: Jira API -> JSONL-файлы в data/raw/ -> три pandas-таблицы
(issues, events, comments) -> метрики. Каждая метрика получает на вход только
эти три таблицы. Ниже — что в каждой, поле за полем.


Уровень 1. Что скачивается с сервера Jira
------------------------------------------

Всё через rest/api/2/search по JQL project = "<ключ>", постранично.
Запрашиваются поля из config/fields.json:

    summary, issuetype, status, priority, assignee, reporter, creator,
    created, updated, resolution, resolutiondate, duedate, labels,
    components, parent, subtasks, issuelinks,
    timeoriginalestimate, timeestimate, timespent

Плюс кастомные поля (ID задаются руками в config/fields.json):
epic_link, story_points.

Результат раскладывается в три JSONL-файла:

    issues.jsonl     сырые issue-объекты со всеми полями выше — качается всегда
    changelog.jsonl  полная история изменений каждой задачи: каждое изменение
                     поля = запись (автор, время, поле, было -> стало).
                     Фаза changelog, опционально.
    comments.jsonl   комментарии (до 100 последних на задачу).
                     По умолчанию выключено.

ВАЖНО: в JSONL лежат все скачанные поля, но не все они доезжают до
аналитических таблиц — часть оседает только в сыром виде (список в конце).


Уровень 2. Аналитические таблицы (src/core/tables.py)
------------------------------------------------------

Таблица "issues" — одна строка на задачу, 17 колонок:

    key              ключ задачи                       CURATOR-123
    summary          заголовок                         текст
    type             issuetype.name                    Bug / Task / Story
    status           текущий статус, имя               "В работе"
    status_category  категория статуса                 To Do / In Progress / Done
    priority         приоритет, имя                    High / Medium... (может быть пусто)
    assignee         исполнитель, displayName          ФИО (может быть пусто)
    reporter         автор, displayName                ФИО
    created          дата создания                     UTC timestamp
    updated          дата последнего изменения         UTC
    resolved_at      resolutiondate                    UTC или NaN
    resolution       резолюция, имя                    Fixed / Won't Do / Duplicate
    duedate          дедлайн                           UTC или NaN
    components       компоненты через запятую          "Backend, API" или пусто
    parent           ключ родителя (для подзадач)      CURATOR-100
    n_subtasks       число подзадач                    int
    timespent_h      затраченное время, часы           float (timespent: сек -> часы)

Таблица "events" — одна строка на каждое изменение любого поля (из changelog):

    key      задача
    time     когда изменили (UTC)
    author   кто изменил (displayName)
    field    какое поле: status, assignee, priority, summary, ... — любые изменения
    from/to  старое и новое значение (текст)

Поверх "events" есть два хелпера:
  - status_events() — только смены статуса, с вычисленными категориями
    cat (куда перешло) и prev_cat (откуда). Основа всех метрик движения
    по процессу.
  - cat_of() — категория статуса по имени: точное соответствие из текущих
    данных, для переименованных/исторических статусов — эвристика по
    ключевым словам (done/closed/resolved..., progress/review/test...,
    в т.ч. русские).

Таблица "comments" — по строке на комментарий:

    key, author, created

Скачивается только при включённой фазе комментариев; сейчас ни одна метрика
её не использует.


Уровень 3. Что скачано, но в таблицы НЕ попадает (только в сыром JSONL)
------------------------------------------------------------------------

  - labels              ярлыки
  - issuelinks          связи задач (blocks, relates to, duplicates)
  - creator             создатель (в таблице только reporter)
  - timeoriginalestimate, timeestimate   оценки времени
  - story_points        стори-поинты (если задан custom field ID)
  - полный текст комментариев (нормализованы только автор/дата)


Что используют текущие метрики
------------------------------

Без changelog (работают всегда):
  overview              типы, статусы, участники
  stale_issues          status_category != Done + updated
  activity_weekly       created, resolved_at, assignee, status_category
  activity_users        то же + updated
  completed_by_assignee resolved_at, status_category, assignee
  discipline_checks     поля гигиены; пункт "закрыто минуя работу" — events
                        (если история есть; без неё 0)

Требуют changelog (метка requires = ("issues", "events"), без истории
в web-интерфейсе отключены):
  lifecycle_cycles      первый переход в In Progress / в Done из status_events
  lifecycle_summary     то же, агрегированно
  rework_issues         переходы Done -> не-Done
  rework_summary        то же, агрегированно


Что можно считать на этих данных (для новых метрик)
----------------------------------------------------

Уже можно без расширений:
  - время пребывания в каждом статусе, "зависание" в Review и т.п.
    (цепочки статусов из events)
  - кто и как часто менял поля, ручные переводы статусов
  - нагрузка/распределение по компонентам, типам, приоритетам
  - трудозатраты: timespent_h по исполнителям/типам
  - иерархия: эпики/подзадачи через parent (частично: эпик-связь
    только в сыром JSONL)
  - резолюции: сколько закрыто как "Won't Do" / "Duplicate"

Можно, но нужно добавить 1-2 поля в tables.py (данные уже скачиваются):
  - issuelinks -> блокировки, дубликаты, граф зависимостей
  - labels -> срезы по ярлыкам
  - creator vs reporter
  - estimate vs timespent -> точность планирования
  - story_points -> velocity

Нужно включать фазу комментариев:
  - метрики коммуникаций
