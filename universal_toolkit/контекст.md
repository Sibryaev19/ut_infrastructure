## 1. Суть проекта

`oarb_premium` — платформенная рабочая область на datalab. Внутри — git-репозиторий
**oarb_toolkit**. Это не просто набор Python-модулей — это **целая база знаний и
экосистема** для работы. Она включает:

- **`modules/`** — Python-модули для работы с разными данными и системами
  (ядро библиотеки, задумано как **большая библиотека / потенциально фреймворк**);
- **`skills/`** — переиспользуемые скиллы (инструкции/шаблоны для агентов и людей);
- **`mcp/`** — конфигурации и серверы MCP-инструментов;
- **`apps/`** — готовые приложения (собираются из модулей или автономные);
- **гайды и best practices** — документация, руководства, принятые практики.

Модулей много и будет ещё больше; проект растёт как **база знаний**, поэтому к
структуре, документированию и тестированию предъявляются повышенные требования
единообразия.

## 2. Структура oarb_toolkit

```
oarb_toolkit/
├── .gitignore
├── README.md                # "# oarb toolkit" (пока пустышка)
├── plan.md                  # дорожная карта по модулям
├── apps/                    # пусто (приложения)
└── modules/
    ├── data_transfer/       # группа «передача данных» (это пакет)
    │   ├── __init__.py      #   реэкспорт: DataCaster, TransferConverter
    │   ├── data_caster/     # модуль потоковой передачи больших файлов
    │   └── outlook_data_transfer/  # модуль архивирования/перекодирования
    ├── database_modules/    # группа «модули БД» (это пакет)
    │   ├── __init__.py      #   реэкспорт: GPConnector
    │   └── gp_tools/        # модуль работы с GreenPlum
    └── utils/               # группа «утилиты» (пока пусто, НЕ пакет)
```

> **Важно о `modules/`:** сам каталог `modules/` **не является** Python-пакетом
> (`__init__.py` в нём нет). Пакетами являются группы — `data_transfer` и
> `database_modules`. Каждая группа реэкспортирует публичный API своих модулей
> вверх, поэтому подключение короткое:
> ```python
> from modules.database_modules import GPConnector
> from modules.data_transfer import DataCaster, TransferConverter
> ```
> `utils/` — каталог без `__init__.py`, пока не пакет (будет им, когда появятся
> модули). Это архитектурная деталь, которую стоит обсудить при консилиуме:
> группы как «неймспейс» уже несут смысловую нагрузку.

### Схема внутреннего устройства модуля
Каждый модуль оформлен единообразно:
```
<модуль>/
├── __init__.py        # реэкспорт публичного класса + __all__ + __version__ = "1.0.0"
├── requirements.txt   # (где нужно) зависимости модуля
└── src/
    ├── __init__.py    # пустой
    └── <core>.py      # реализация класса
```
Публичный API реэкспортируется в `__init__.py` модуля, поэтому импорт для
пользователя — короткий, например:
`from modules.database_modules.gp_tools import GPConnector`.

## 3. Текущее содержимое модулей

### 3.1 `database_modules/gp_tools` — GPConnector (готов, протестирован)
- **Файл:** `src/gp_connector.py`
- **Публичный API:** `GPConnector(host, dbname, port, login)`
- **Возможности:**
  - `connect()` / `close()` — подключение к GreenPlum (GSS/Kerberos,
    `gssencmode=prefer`; user из `JUPYTERHUB_USER`).
  - `sql(query)` — аналог `spark.sql`, возвращает **pandas DataFrame**
    (через Polars с явной схемой, маппинг OID→тип Polars, каст нестандартных
    объектов в строки).
  - `run_maintenance(query)` — VACUUM / REINDEX вне транзакции (autocommit).
  - `to_parquet(query, dir, batch_size, schema)` — потоковая выгрузка батчами
    в parquet (серверный курсор).
  - `to_parquet2(query, dir, num_partitions, batch_size)` — выгрузка через
    `DECLARE ... CURSOR WITH HOLD`, предрасчёт на сервере для тяжёлых запросов.
  - `OID_TO_POLARS` — большой словарь маппинга типов (базовые, системные, массивы).
- **Зависимости:** `psycopg`, `polars`, `pandas` (+ `pyarrow`).
- **Статус:** smoke-тест пройден (`develop/gp_tools/smoke.py`) на стенде:
  connect / sql / маппинг типов OID→Polars→Pandas работают. **Тестирование закрыто.**

### 3.2 `data_transfer/data_caster` — DataCaster (код есть, тестов не видно)
- **Файл:** `src/data_caster.py`
- **Публичный API:** `DataCaster()`
- **Возможности:** быстрая потоковая передача больших файлов между машинами в
  локальной сети через HTTP (FastAPI + uvicorn + requests).
  - Сторона А (раздающий): `create_proxy(port)`, `set_load(name, paths)`, `stop()` —
    поднимает сервер, регистрирует загрузки, отдаёт файлы с поддержкой Range.
  - Сторона Б (скачивающий): `connect(address)`, `check_loads()`, `download(...)`
    с докачкой и контролем размера.
- **Зависимости:** `fastapi`, `uvicorn`, `requests`, `tqdm`.
- **Статус:** код реализован, тестов в репозитории/на стенде не обнаружено.

### 3.3 `data_transfer/outlook_data_transfer` — TransferConverter (код есть, тестов не видно)
- **Файл:** `src/transfer_converter.py`
- **Публичный API:** `TransferConverter(add_extension, remove_extension)`
- **Возможности:**
  - `create_zip_with_renamed_files(...)` — упаковка папки в ZIP с переименованием
    расширений файлов (обход ограничений почтовых систем).
  - `extract_and_restore_names(...)` — распаковка с восстановлением имён
    (решает конфликты суффиксами).
  - `bin_file_to_base64(...)` / `base64_to_bin_file(...)` — бинарный файл
    ↔ base64 (+ права `0o755` на восстановленном бинарнике).
- **Зависимости:** только стандартная библиотека (`zipfile`, `base64`, `argparse`...).
- **Статус:** код реализован, тестов не обнаружено.

### 3.4 `utils` — пусто
Группа создана, модулей пока нет.

Рядом с проектом существует каталог **`/home/datalab/nfs/utool_dir`** — плоский
набор скриптов («утилки»), из которого **часть модулей уже переехала** в oarb_toolkit

### 4.1 Содержимое `utool_dir` (без `loads/`)

| Единица | Назначение | Статус по отношению к oarb_toolkit |
|---|---|---|
| `distributed_task/` (v2.1.0) | `DistTask` — распределённая обработка очереди данных; `Podnet` — P2P-связь воркеров. Именно это и есть `disttask` из plan.md | **кандидат на перенос** (в oarb_toolkit пока нет) |
| `PodnetProxy.py` | `PodnetProxy` — прозрачный HTTP-прокси между контейнерами через Podnet (режимы target/client, FastAPI) | **кандидат на перенос** |
| `zip_backup.py` | `ZipBackup` — zip-бэкап с манифестом (sha256) и git-подобной сверкой структуры (DELETED/MODIFIED/ADDED/RENAMED) | **кандидат на перенос** |
| `Reproducer.py` | `CodeLinter` (pylint/sqlfluff/ruff) + `Reproducing` (автоматический git clone/commit/push с вводом пароля) | **кандидат на перенос** (инструменты разработчика) |
| `custom_spinner.py` | `set_custom_spinner` — кастомный спиннер JupyterLab (CSS/JS через IPython) | **кандидат на перенос** (оформление/datalab) |
| `data_caster.py` | потоковая передача больших файлов (FastAPI) | **уже перенесён** → `data_caster` |
| `gp_connector.py` | подключение к GreenPlum (OID→Polars→Pandas) | **уже перенесён** → `gp_tools` |
| `zip_converter.py` | `ZipExtensionsConverter` — zip + смена расширений + base64 | **уже перенесён** → `outlook_data_transfer` (как `TransferConverter`) |

### 4.2 Наблюдения (важно для архитектуры)
1. **Перенос уже идёт стихийно**: 3 из 8 единиц мигрировали. Причём в одном случае
   (`zip_converter` → `outlook_data_transfer`) перенос почти копия — класс
   `ZipExtensionsConverter` стал `TransferConverter` с тем же кодом. Это значит,
   что «миграция = копирование» уже происходит без единого процесса.
2. **Нейминг не согласован**: в utool_dir имена файлов и классов разные
   (`data_caster.py`/`DataCaster`, `zip_converter.py`/`ZipExtensionsConverter`),
   а в oarb_toolkit единый шаблон `src/<core>.py` + реэкспорт. Источник-донор
   этому шаблону не следует.
3. **Смена имён классов при переносе** ломает обратную совместимость со старым
   кодом (`ZipExtensionsConverter` → `TransferConverter`). Надо решить, делаем ли мы
   миграцию с алиасами/ренеймом.
4. **Кандидаты на перенос** разной тематики: сеть/распределёнка (`distributed_task`,
   `PodnetProxy`), утилиты (`zip_backup`), инструменты разработчика (`Reproducer`),
   оформление datalab (`custom_spinner`). Это прямо влияет на **группы модулей**:
   появятся ли `networking`, `utils`, `datalab`.

## 6. Масштаб: модулей будет МНОГО

Ключевой факт про проект: **модулей много, и будет ещё больше**. Это не 3–5
классов, а основа для большой библиотеки / фреймворка. Уже сейчас заявлены
группы `data_transfer`, `database_modules`, `utils` и планы на новые модули
(datalab, оформление, venv, disttask, GPTool, ...), и это только верхушка.

**Важно:** растёт не только `modules/` — **вся база знаний** (скиллы, mcp, apps,
гайды, best practices) тоже будет расширяться. Поэтому принципы единообразия,
реестра и навигации надо закладывать на уровень **всего репозитория**, а не только
кода.

Из этого следуют требования, которые должны быть заложены в архитектуру **сейчас**,
пока модулей мало:
- **Единообразие структуры** — каждый модуль уже собран по одному шаблону
  (см. раздел 2). Это надо сохранить и закрепить.
- **Автомасштабируемый импорт** — не хардкодить `sys.path` в каждом скрипте,
  а дать единый механизм.
- **Единый способ тестирования** — если модулей много, разовые smoke-скрипты
  не работают; нужны согласованные тесты и раннер.
- **Реестр/метаданные модулей** — знать, какие модули есть, их версии, зависимости.
- **Единый публичный интерфейс** — короткий импорт и единый стиль ошибок/логики.

Это и есть суть открытой задачи по архитектуре (см. раздел 10).

## 8. Архитектура — открытые вопросы для консилиума

Главная развилка: проект превращается из «набора скриптов» в **большую библиотеку /
фреймворк и целую базу знаний** (модули + скиллы + mcp + apps + гайды/best practices).
Пока модулей мало, нужно зафиксировать архитектурные решения.
Ниже — вопросы, на которые стоит получить консилиум (человека или ИИ).

### 8.1. Упаковка и распространение
- Делать ли `oarb_toolkit` полноценным пакетом (`pyproject.toml` / `setup.py`,
  установка `pip install -e .`) или оставить как «папку с модулями» + подхват
  через `sys.path`?
- Нужен ли единый импорт `import oarb_toolkit` / `from oarb_toolkit.modules...`
  против текущего `from modules...`?
- Учитывать заморозку среды (Python 3.8 и др.).

### 8.2. Структура и неймспейсы
- Группы (`data_transfer`, `database_modules`, `utils`, ...) как постоянный
  уровень вложенности — достаточно ли его для масштаба «много модулей»?
  Не понадобятся ли вложенные группы / версии модулей?
- Нужен ли `__init__.py` на уровне `modules/` (сейчас его нет — `modules` не пакет).

### 8.3. Единый механизм работы с модулями
- Общий класс/реестр модулей: метаданные (группа, версия, зависимости, статус),
  проверка импортов, единый способ запуска.
- Единый способ подхвата корня репозитория в `sys.path` (сейчас хардкод в каждом
  smoke-скрипте) — вынести в общий модуль/утилиту.

### 8.4. Миграция из `utool_dir`
- Единый процесс переноса модулей-доноров (см. раздел 4): рейнем классов/файлов,
  обратная совместимость (алиасы), тесты при переносе.
- Разбивка кандидатов по группам (`networking` для `distributed_task`/`PodnetProxy`,
  `utils`, `datalab` для `custom_spinner`).

### 8.5. Тестирование
- Фреймворк тестов (pytest), где живут тесты (в git рядом с модулями или на стенде
  `develop/`), фикстуры/маркеры, CI или локальный раннер.
- Как тестировать модули с внешними зависимостями (GP + Kerberos, сеть, БД):
  моки/фикстуры против реальных подключений.

### 8.6. Среда запуска
- В какой среде работаем: базовый venv проекта vs локальные `--target`-папки +
  `PYTHONPATH`. Как разруливать версии под разные Python (после проблем с диском
  на общем кластере).

### 8.7. Структура базы знаний (не только модули)
Проект — это **экосистема**, а не только `modules/`. Нужно заранее определить, как
уживаются части и где их границы:
- **`modules/`** — Python-модули. Это «код».
- **`skills/`** — переиспользуемые скиллы/инструкции для агентов и людей. Как
  связаны с модулями (оборачивают их? автономны?)?
- **`mcp/`** — серверы/конфигурации MCP-инструментов. Как соотносятся с модулями
  (модуль может быть «за MCP-обёрткой»)?
- **`apps/`** — готовые приложения, собранные из модулей или автономные. Какова
  связка «модуль → приложение»?
- **гайды / best practices** — знания. Где живут (корень? `docs/`?), как
  версионируются и связываются с кодом.
- Единый стиль каждого блока (шаблон), навигация/реестр по всей базе знаний.

## 10. Открытая задача: как организовать работу и тестирование большой библиотеки

### Проблема
Тестировать текущие модули **неудобно**. oarb_toolkit задуман как огромная
библиотека (возможно, фреймворк) и база знаний, поэтому нужно заранее решить,
**как именно** строить работу с ним: структуру, тесты, способы
подключения/запуска, единый механизм. Сейчас тесты на стенде — разовые `*.py`
скрипты без общей дисциплины.

> Архитектурные вопросы более широко раскрыты в разделе **8. Архитектура —
> открытые вопросы для консилиума**. Здесь — конкретика по тестированию.

### Что нужно решить (на обсуждение)
