# context — universal_toolkit

## Что это
`universal_toolkit` — универсальная среда и библиотека модулей. Разрабатывается
здесь (ноут Windows + домашний Linux), переносится в контур компании (Linux datalab,
без интернета). Репозиторий живёт внутри `funny_projects` — сознательный выбор
пользователя, переезд в отдельный репозиторий не планируется.

**Двойное имя (2026-11-27):** один и тот же тулкит в **git называется
`universal_toolkit`**, а **в datalab будет называться `oarb_toolkit`**.
Имя импорта зависит от площадки; как именно будет переключаться имя при
переносе — обсудить на этапе переноса в контур. Имя репо/пакета здесь
НЕ переименовывать.

Роли:
- **`universal_toolkit`** — новое решение, проектируется с нуля.
- **`source/oarb_toolkit/`** — легаси-дамп кода (38 файлов), источник для новых
  модулей; перенесён в `source/` 2026-11-27, чтобы не мешать новой структуре.
- **`UTool.py`** — легаси-вход, живёт в `/home/datalab/nfs/UTool.py`, ноутбуки
  находят его через `sys.path.append("/home/datalab/nfs")`. Разбирается на модули,
  его API — привычка пользователя, которую сохраняем шимом.

Исходное описание проекта — `../контекст.md`.

## Зачем это всё (суть, слова пользователя 2026-11-26)
Работа — datalab, преимущественно Jupyter-ноутбуки. Технологии: GP, HDFS,
trino, hive, обработка данных, LLM, модели. Почти со всем приходится разбираться
с нуля; с некоторыми технологиями никто не знаком или знакомы единицы.
**Модули — для ежедневного ручного использования, не для приложений**, где
настраиваешь один раз и забываешь. Если при каждом использовании надо писать
простыни настроек (как у spark-сессии) — инструмент просто отвергнут
(к спарк привыкли, новое с порогом входа не примут). Репозиторий с готовыми
модулями и шаблонами — чтобы люди не разбирались с нуля.
**Борьба идёт за удобство**: «импортировал UTool — и дальше вызываешь через него».

Уточнения (2026-11-26):
- UTool-ом пользовался **только сам пользователь**; oarb_toolkit будет
  **общедоступным**. Старички UTool не видели: они поднимают spark-сессию
  руками в блокнотах, а с GP работают копипастом из своих старых блокнотов
  (pandas + psycopg2, курсоры напрямую). Значит для них новый функционал —
  **не замена привычек, а новые возможности**; сохранять их «ритуал UTool»
  не нужно. Гайды — в специальной папке; туда же подключаются агенты
  (инструкция для них) — подсказки для людей.
  Видение удобства пользователя может быть необъективным — он готов
  пересматривать и принимать критику.
- **Удобство системы достигается классами-агрегаторами.** Модули проектируются
  независимо и по возможности универсально; удобство — не их забота, а фасада.
- **Агрегируем только модули.** Шаблоны, скиллы, mcp, приложения, «примеры» —
  самостоятельные единицы или части другого; их не трогаем. Модуль — среднее:
  слишком самостоятелен для скилла, недостаточно самостоятелен для приложения,
  и их много — потому и объединяем.

## Глобальные требования (шаг 1)
Проект большой, в одном чате не делается. Репозиторий развивается постоянно.

1. **Две машины, три площадки**: ноут (Windows), домашний Linux-комп (там же
   имитация datalab), контур компании. Код живёт в **git** — единственный источник.
2. **Код не только для datalab**: модули под разные задачи и разные ОС.
3. **`source/`** — архив-донор (бывш. план «old/»). Легаси `oarb_toolkit/`
   перенесено туда 2026-11-27; новая архитектура строится рядом, опираясь
   на source. По завершении проекта папка удаляется.
4. **Главное — удобство пользователя.** Опора на клиентский путь, не на
   формальности и документацию.
5. Каждый модуль пересматривается заново: улучшить / объединить / разделить.
6. **Тестируем всё.** При необходимости на Linux-компе ставится HDFS, Greenplum.
7. Репозиторий — не только модули, а **полноценная среда** (skills, mcp, apps, guides).

## Контракт параметров модуля (согласован 2026-11-26)

Три группы:
1. **Фиксированные** — в этой системе не меняются. Хардкод в модуле; сам объект
   создаётся лениво, не при импорте.
2. **Входные** — меняются при каждом вызове. Всегда явные, дефолтов нет.
3. **Почти-константы** — меняются редко, дефолт нужен в 95% случаев. Дефолт живёт
   в модуле и выражается через `None`.

Всё остальное — внутреннее состояние и вычисленные значения — не параметры
и в сигнатуру не попадает.

Секреты — не фиксированные и не дефолты: только извне, никогда не логируются.

Правила:
- **Владелец дефолта — владелец `META`.** Модуль под систему хранит почти-константы
  у себя; portable-модуль дефолтов не имеет — его параметры обязательные.
- **Дефолт выражается через `None` и разворачивается внутри модуля.** Агрегатор
  объявляет те же имена с `None` и передаёт как есть — ноль литералов, ноль копий.
- Агрегатор владеет только сессионным знанием — кто я сейчас. Всё, что задаётся
  системой, а не пользователем, — константа модуля, не сессии.
- **`import` без побочек**: никаких соединений, чтения env, настройки логгеров —
  всё лениво и в экземпляре.

## Легаси-аудит (факты о коде в `oarb_toolkit/`)
- `UTool.py` — 700 строк, v3.1: spark-сессия, файлы, excel, pickle, HDFS, CSS
  ноутбука в одном классе.
- Побочки на импорте: `JUPYTERHUB_USER` без fallback, два HDFS-подключения
  с Kerberos, `display(HTML(...))`, тяжёлые импорты (pyspark, psycopg, dill).
- `UTool.get_gp_connector()` берёт `utool_dir.gp_connector`, а не новый модуль.
- `from utool_dir.distributed_task import ...`, хотя пакет лежит в корне
  `distributed_task/` — импорт не соответствует дереву.
- f-string на строке 205 вложенными кавычками — валиден только на 3.12 (не баг).
- `get_view_list()` объявлен без `self`.
- Дубли: `utool_dir/data_caster.py`, `gp_connector.py`, `zip_converter.py`.
- Нет `modules/__init__.py`; в requirements опечатка `request` вместо `requests`.
- В `utool_dir/` 7 скриптов, включая `trino_connector.py` (не упомянут в контексте).

## Тестирование datalab-модулей (2026-11-27)
Решение пользователя: datalab-модули готовим с **полноценными окружениями
и тестами на стенде local_datalab** (jupyterhub в Docker, DockerSpawner,
workspace = `/home/datalab/nfs`) — до смоука в контуре. Три уровня:
юнит-тесты (везде) → стенд (datalab-поведение) → смоук в контуре (приёмка).
Стенд не равен контуру (Kerberos/GP свои) — не заменяет смоук.

**Границы проектов:** local_datalab — отдельный git-репозиторий и отдельный
чат (разделение работ 2026-11-27); в этом чате — только разработка модулей.
Изменения платформы — коммиты в local_datalab, модулей — в universal_toolkit.
Связь — только по путям (монтирование/копирование папки toolkit'а в
workspace при запуске), файлы toolkit'а внутрь local_datalab не попадают.
