# plan — архитектура universal_toolkit

Статус: **confirmed (видение)** · 2026-11-26 · шаги 1–2 пройдены
Согласовано с пользователем 2026-11-26 после сессии: разбор трёх модулей,
эксперимент dep_demo, фасад/доктор/уровни. Это — инструкция и контекст для
будущей реализации скелета (после того, как будут разобраны реальные модули).
Действия по созданию — только по приказу пользователя.

## Цель
Универсальная среда: удобно в Jupyter, в скриптах и в разработке; на Windows и
Linux; в контуре без интернета и снаружи. Главный критерий — клиентский путь
(удобство), а не формальности. Модули — для ежедневного ручного использования,
не для приложений: если вход требует простыни настроек — инструмент отвергнут.

## Слои
```
knowledge   guides, examples        ← знания, ничего не импортируют
surfaces    ноутбук, CLI, MCP, apps ← самостоятельные единицы
facade      геттеры + доктор        ← композиция и ленивое создание
modules     возможности              ← независимые, переносимые
core        конфиг, реестр, ошибки   ← без внешних зависимостей
```
Зависимости — только вниз. Агрегируются ТОЛЬКО модули; guides/examples/skills/
mcp/apps — самостоятельные или части другого, их не трогаем. Guides — в
специальной папке; туда же инструкция для агентов-подсказчиков.

## Идея: среда → фасад → модули
- Импорт без побочек: никаких соединений, чтения env и логгеров на импорте.
- Модуль знает свои системные константы (хосты fsspec, kerberos, spark-сессия):
  это его природа, а не окружение. Сессионное (кто я сейчас, JUPYTERHUB_USER)
  приходит параметром; модуль его не знает.
- Модуль не трогает sys.path и не вычисляет пути к самому себе.
- Фасад ничего не реализует: композиция и ленивое создание.

## Фасад (агрегатор) — решено 2026-11-26
Основа — типизированные фабричные геттеры (вариант 1) + прямой импорт
(вариант 3). Атрибутный сахар (`t.gp`) в основной фасад НЕ входит.

```python
t = Toolkit()
gp = t.get_gpconnector()      # настроенный экземпляр; параметры можно:
                              #   t.get_gpconnector(dbname="другая")
dt = t.get_disttask()         # каждый модуль — свой геттер
t.available()                 # что здесь работает и почему нет

from universal_toolkit import GPConnector          # дверь для продвинутых:
from universal_toolkit.modules.data_transfer.data_caster import DataCaster  # напрямую, мимо геттеров
```

- Геттер = composition root: место, где сессионное знание встречается
  с константами модуля; читается как меню возможностей (`t.get_` + Tab).
- Гейт `_gate` (одна механика для всех геттеров): композиция. Доктор добавится
  в гейт после его отдельной проработки.
- **Кэша НЕТ** (решено 2026-11-26): каждый вызов геттера = новый экземпляр.
  Возникнут проблемы (тяжёлые пересоздания) — пересмотрим.
- Сахарный модуль «популярного функционала» на основе UTool: отдельный модуль
  для короткого синтаксиса (`utool.save_excel(df, path)`). Правило: сахар =
  ТОЛЬКО проброс вызовов через те же геттеры, ноль своей логики.
- Конвенция для guides: новичок всегда начинает с `t.get_...`; прямой импорт —
  «когда понимаешь, что делаешь».

## Доктор — модуль проверки окружения
**Отложен 2026-11-26 на отдельную проработку** — вещь сложная, делать без
обсуждения не будем. Концепция ниже — видение, не приказ к реализации.
- Живёт в группе системных модулей — `modules/system/` (имя решено 2026-11-26).
- Хук: при ПЕРВОМ обращении через геттер проверяет зависимости только этого
  модуля; полный скан — по явному вызову `t.doctor()`.
- Отчёт: чего не хватает + как починить (в контуре — без pip: положи wheel,
  `pip install --no-index`).
- Неиспользуемый модуль не проверяется вовсе (trino не установлен — и не нужен,
  пока не обратились).
- Источник правды о зависимостях — `requirements.txt` (решено 2026-11-26,
  единообразие); детали чтения — при проработке доктора.
- Кандидаты той же группы: `freeze` (снимок окружения для переноса между
  машинами), генерация requirements.

## Уровни популярности — витрина, а не место хранения (решено 2026-11-26)
- Дерево модулей — ТОЛЬКО по доменам (`databases/gp_tools`,
  `data_transfer/data_caster`). Папки `special/`/`popular/` НЕ заводить:
  «special» — мусорная корзина по определению; популярность изменчива,
  а путь импорта — обещание (переезд ломает чужие блокноты).
- Популярность — это короткая дверь: топ-реэкспорт в `universal_toolkit`
  (`from universal_toolkit import GPConnector`) + короткий геттер.
- Специфичный модуль: тот же единый геттер `t.get_datacaster()` (меню общее)
  + честный длинный путь импорта, который никогда не меняется.
- Смена уровня = строка в витрине (алиас), не переезд файла.

## Раскладка (решено 2026-11-26: репозиторий и есть пакет)
```
universal_toolkit/            # репозиторий, ОДНОВРЕМЕННО импортируемый пакет
├── __init__.py               # витрина: топ-реэкспорт популярных + Toolkit
├── facade.py                 # фасад — важный класс, в корне пакета
├── core/                     # реестр, ошибки, конфиг
├── modules/                  # группы по доменам + system/; sugar/ — тоже модуль
├── guides/                   # examples + инструкция для агентов — часть пакета
├── source/                   # ВРЕМЕННО: донор (oarb_toolkit/, 38 файлов,
│                              #  перенесён 2026-11-27); удаляется по завершении
├── develop/                  # ВРЕМЕННО: песочница (вне git); удаляется по завершении
├── .for_agent/               # в git: контекст агента между машинами
├── .gitattributes / .gitignore / pyproject.toml
└── контекст.md
```
- Репозиторий = пакет: `__init__.py` в корне, весь репо импортируется целиком
  (`from universal_toolkit import Toolkit`). Импорт: корень funny_projects
  в `sys.path` одной строкой.
- `source/` и `develop/` — временные элементы разработки; по завершении удаляются,
  пакет остаётся чистым. Временность оправдывает их присутствие в дереве.
- guides/skills/apps — части репозитория-пакета, не внешние папки.

## Группы модулей (гипотеза, уточняется при пересмотре модулей)
`databases`, `data_transfer`, `distributed`, `spark_tools`, `file_tools`,
`system`. Группа — домен, среда — метаданные (META).

## Две машины
- `.gitattributes` → LF везде; ни одного абсолютного пути в коде.
- `META.os` честно разделяет платформенные и кроссплатформенные модули.
- venv на каждой машине свой, в git нет.
- Тесты — в git (решено 2026-11-26).
- Прогоны на ноуте: `PYTHONIOENCODING=utf-8` без `-I` (консоль cp1251).

## `source/` как донор
Переносим по одному модулю. Новый модуль рождается с паспортом и тестом.
Дубли удаляются после сверки. `source/` — не пакет и не на пути импорта.
